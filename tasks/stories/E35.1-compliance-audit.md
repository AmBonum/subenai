# E35.1 — Compliance audit report (declaration↔implementation matrix)

**Epic:** [E35 — Security & GDPR compliance audit + test coverage expansion](../PLAN-2026-05-20-E35-security-compliance-audit.md)
**Effort:** `M` (≤ 2 days)
**Priority:** `P0` (blocker — drives all sibling stories)
**Status:** 🟡 Ready

## Context

The four public legal pages — `/privacy`, `/cookies`, `/manage-support`,
`/about` — make ~60 concrete declarations about how subenai handles user
data, cookies, consent, retention, third-party processors, and GDPR rights.
Without a row-by-row verification that each claim is backed by code, we
have no way to know whether we're honest with our users or our regulator.

This story produces that matrix as a single Markdown deliverable. The
output is **not** a code change — it's a research artefact whose contents
drive E35.2–E35.7 (which gaps become failing tests now) and E36+ (which
gaps become future implementation epics).

## User story

> As the project owner, **I want** every claim on the four legal pages
> cross-referenced to either a file:line of code or a "missing" verdict,
> **so that** I can answer "are we actually GDPR-compliant?" with evidence
> rather than belief.

## Acceptance criteria

- **AC-1**: The matrix lives in this story file under `## Matrix`. One row
  per claim, columns: `Claim ID | Page | Slovak quote (truncated to 120
  chars) | English gloss | Status (✅ / ⚠️ / ❌) | Evidence | Follow-up`.
- **AC-2**: Every claim listed by the recon agents (privacy: ~28 claims,
  cookies: ~11, about: ~8, manage-support: ~5) is present in the matrix.
  Final count ≥ 50 rows.
- **AC-3**: Every `Evidence` cell either cites a file:line (preferred) or
  a migration filename, or — for `❌` rows — explicitly says "no
  implementation found".
- **AC-4**: Every `Follow-up` cell maps to one of:
  - "Covered by E35.2"–"E35.7" (a failing test in this epic), OR
  - "Future epic E36/E37/E38/E39/E40" (deferred implementation), OR
  - "Legal copy correction needed in E35.1 follow-up CHANGELOG" (rare —
    only when the page overstates reality and the fix is "tone it down").
- **AC-5**: A summary table at the bottom counts rows by status emoji and
  by follow-up bucket, so the reader gets the punch list at a glance.

## Subtasks

### Implementation

- [ ] Read the full source of `src/routes/privacy.lazy.tsx`,
      `src/routes/cookies.lazy.tsx`, `src/routes/about.lazy.tsx`,
      `src/routes/manage-support.tsx` and extract every claim verbatim.

      component) and fill the Evidence column with file:line.
- [ ] Classify each row as ✅ / ⚠️ / ❌ per the rule:
      - ✅ = code matches claim exactly

        or feature exists but doesn't cover every case the page implies)
      - ❌ = no implementation found, or implementation contradicts claim
- [ ] Roll the `❌` and `⚠️` rows into a punch list in the summary section.

which gaps to test for. Sibling stories can start in parallel using the

of E35.2–E35.7 depends on the final matrix to confirm no gap was missed.

### Headline gaps

The four `❌` retention rows (P-4, P-6, P-7, P-20) collapse to **one root cause**: pg_cron is commented out across all migrations. Either the operator has enabled it manually in the Supabase dashboard (in which case it's a documentation issue — the migrations should reflect reality) or it's not enabled (in which case the legal copy overstates reality and either the copy must be toned down or E38 must enable the crons).

The five `❌` cross-cutting rows (X-1 to X-5) collapse to **one root cause**: no automated test asserts that "code-level cookie / localStorage writes" ⊆ "declared cookie / localStorage table". E35.4 will close that loop with a no-leak journey assertion that compares observed cookies + localStorage keys against an allowlist.
