# E48.2 — Storage bucket + deterministic attachment sanitisation pipeline

**Epic:** E48 — Support contact form + admin ticketing system
**Effort:** `M` (~2 days; was `L` before D-1 dropped the VirusTotal scanner)
**Priority:** `P0`
**Status:** 🟡 Ready
**Branch:** `feature/E48-support-ticketing`
**Commit prefix:** `feat(security):`
**Dependencies:** E48.1 (schema must exist before we can write attachment rows)

## Context

The most security-sensitive story in the epic and the one with the
highest delivery risk. The goal: accept user uploads (JPG / PNG / PDF
only, max 5 files × 5 MB each), deterministically sanitise them at the
edge, store them in a private Supabase Storage bucket, and only retain
files that pass sanitisation. Per PLAN D-1 (decided 2026-05-21):
**no third-party AV** — sanitisation is the only line of defence, and
that defence is structural (re-encode every image, rewrite every PDF).
A file that passes sanitisation is, by construction, `clean`.

PLAN §"Architecture > Storage bucket" and §"CF Pages Functions" describe
the pipeline. PLAN §"Security review checklist" enumerates the attack
surface this story closes.

## Acceptance criteria

- **AC-1:** Supabase Storage bucket `support-attachments` provisioned (private — no public read policy). `storage.objects` RLS: only admins SELECT; INSERT via service-role-bearing Pages Function. Bucket creation goes into `supabase/migrations/<ts>_e48_2_support_storage_bucket.sql` (idempotent — uses `INSERT INTO storage.buckets … ON CONFLICT DO NOTHING`).
- **AC-2:** New deps installed: `sharp` (image re-encode), `pdf-lib` (PDF rewrite), `file-type` (magic-byte sniffing). Compatibility spike commit lands BEFORE the rest of the story — prove `sharp` (preferably via `@cf-wasm/sharp` or `sharp/wasm`) loads inside a Pages Function. Document the runtime choice in the runbook. If neither WASM build works, fall back to `jimp` for images (PDF path stays on `pdf-lib`).
- **AC-3:** `/functions/api/support-attachment-upload.ts` accepts `multipart/form-data` POST with one file + `ticket_id` + `view_token` (anonymous) or `Authorization: Bearer <jwt>` (authenticated). Validates:
  - filename ≤ 200 chars; non-conforming chars stripped (allowed character class `[A-Za-z0-9._\-]`); extension preserved
  - declared MIME ∈ `{image/png, image/jpeg, application/pdf}` (rejects everything else; no `image/svg+xml`, no `application/octet-stream`, no `text/html` masquerading as image)
  - file size ≤ 5 MB
  - **magic bytes match the declared MIME** via `fileTypeFromBuffer` (rejects MIME-confusion attacks)
  - rate-limited per ticket — max 5 attachments per `ticket_id`
- **AC-4:** Sanitisation pipeline (deterministic, structural):
  - **Images** (PNG / JPEG): decoded + re-encoded via `sharp`, output PNG-from-PNG or JPEG-from-JPEG (no cross-format conversion). EXIF, ICC, XMP and all metadata stripped. **Image-bomb cap**: refuse if decoded pixel count > 40 megapixels OR width/height > 12000 px.
  - **PDFs**: re-saved via `pdf-lib`, stripping (Phase-A review H-S1 added entries in **bold**) `/JS`, `/JavaScript`, `/AA`, `/OpenAction`, `/Launch`, `/SubmitForm`, `/RichMedia`, `/3D`, `/Movie`, `/Sound`, **`/EmbeddedFile`, `/Filespec`, the `Names → EmbeddedFiles` sub-tree**. `/AcroForm` field scripts removed. `/URI` annotations stripped (clickable links → plain text). **JBIG2 / JPX-decode awareness (H-S2)**: reject (400 `code: 'unsupported_filter'`) any PDF whose image streams contain a `/Filter` array including `JBIG2Decode` or `JPXDecode` — these decoders bypass `sharp` and have a history of viewer-CVE exploit chains. Document the residual risk for *other* image filters in `tasks/E48-runbook.md` §3 (threat model).
  - **PDF-bomb cap**: refuse if page count > 50 OR raw byte-size of any single page object > 2 MB after re-save.
  - If sanitisation throws (corrupt file, unparseable PDF, bomb caps exceeded) → 400 with `{ code: 'sanitization_failed', detail: '<safe-to-show description>' }`. **No row is inserted; no Storage object is written.** The user sees a Slovak error in the form: "Súbor nemohol byť bezpečne spracovaný."
- **AC-5:** Sanitised file uploaded to `support-attachments/<ticket_id>/<uuid>.<ext>` via Supabase Storage SDK using the service-role key. `support_ticket_attachments` row inserted with `scan_status='clean'`, `scan_provider='deterministic'`, `mime_type` set to the **verified** MIME (not the declared one), `size_bytes` set to the **post-sanitisation** size, `checksum_sha256` of the sanitised bytes.
- **AC-6:** `request_attachment_signed_url(p_attachment_id)` RPC (from E48.1) returns a 15-min signed URL when `scan_status='clean'` AND `auth.uid()` belongs to an admin with `aal2`; raises `not_authorized` or `not_clean` otherwise. Audit-logged via `audit_log` row `action='support_attachment_download_url_issued'`.
- **AC-7:** Error responses NEVER leak internal paths, stack traces, or sanitisation library version strings. The Slovak user-facing string is fixed-set: "Súbor nemohol byť bezpečne spracovaný." / "Súbor je príliš veľký." / "Nepodporovaný formát súboru." / "Príliš veľa príloh." / "Príliš veľa pixelov v obrázku." / "PDF má príliš veľa strán."

## Open questions

- **Should `support-attachments` bucket allow direct user re-download of their own attachment via the view-token URL?** *Lean: no for now — view-thread page shows filename + size + a "súbor je k dispozícii len pre administrátora" note.* Avoids issuing signed URLs to unauthenticated clients. If user feedback justifies it, add a token-gated download path in a follow-up.
- **`@cf-wasm/sharp` vs `sharp/wasm` vs `jimp` — which performs best in the Workers runtime?** Decide in the spike commit. `jimp` is pure JS, slowest but most portable. `sharp/wasm` is fastest but bundle-heavy.
- **Should we hash the **original** file too (pre-sanitisation), for future "did the user upload exactly this byte sequence?" forensics?** *Lean: no — original bytes are not stored, so the hash has no anchor.* If a future VT integration arrives, that flow will hash the original.
