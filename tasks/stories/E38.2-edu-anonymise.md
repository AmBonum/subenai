# E38.2 — Edu mode auto-anonymisation function

**Epic:** [E38 — Retention crons + auto-anonymisation](../PLAN-2026-05-20-E38-retention-crons.md)
**Effort:** `S` (≤ ½ day)
**Priority:** `P1`
**Status:** 🟡 Ready

## Context

`/privacy` s8 declares 12-month edu retention, then "potom automaticky
meno a e-mail anonymizujeme (skóre + odpovede zostávajú pre štatistiku
autora)". Today the columns `attempts.respondent_name` and
`attempts.respondent_email` (added by
`supabase/migrations/20260501000000_edu_mode.sql`) are not anonymised
on any schedule. They get deleted only when the whole row hits
36-month retention.

We add `public.anonymize_expired_edu_respondents()`.

## Acceptance criteria

- **AC-1**: New migration
  `supabase/migrations/{ts}_edu_anonymise.sql` creates
  `public.anonymize_expired_edu_respondents()` as a
  `SECURITY DEFINER` function with pinned
  `search_path = public, pg_temp`.
- **AC-2**: Function updates `attempts` rows where:
  - `respondent_name IS NOT NULL` OR `respondent_email IS NOT NULL`
  - AND `created_at < now() - interval '12 months'`
  Sets both columns to NULL. Returns row count as INT.
- **AC-3**: Function preserves `final_score`, `share_id`, `breakdown`,
  any answer JSONB — only `respondent_name` + `respondent_email`
  become NULL.
- **AC-4**: GRANT EXECUTE to `service_role`; REVOKE EXECUTE from
  `PUBLIC`.
- **AC-5**: Author-dashboard query (`get_set_attempts` or similar in
  `supabase/migrations/20260501000000_edu_mode.sql`) must still render
  anonymised rows without crashing. If it errors when `respondent_name
  IS NULL`, surface that as a separate bug in this story.
- **AC-6**: `DEPLOY_SETUP.sql` includes the new migration (E38.5).
