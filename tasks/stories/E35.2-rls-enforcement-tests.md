# E35.2 — Live-SQL RLS & SECURITY DEFINER enforcement suite

**Epic:** [E35 — Security & GDPR compliance audit + test coverage expansion](../PLAN-2026-05-20-E35-security-compliance-audit.md)
**Effort:** `L` (≤ 1 week)
**Priority:** `P1` (must)
**Status:** 🟡 Ready

## Context

Today's `tests/security/rls-shape.test.ts` confirms RLS policies *exist*
on each table by reading `pg_policies`. It does **not** confirm that the
policies do what they claim. The difference is real: a policy can exist
with `USING (true)` and pass shape tests while letting any anon caller
read every row.

This story adds integration tests that **actually sign in** as anon,
user A, user B, and admin against a local Supabase, then assert each
sensitive operation succeeds or fails per the documented contract. It
also covers the `SECURITY DEFINER` functions (`has_role`,
`log_audit_event`, the three respondent RPCs) and the immutability
triggers (`forbid_attempt_score_changes`, `forbid_audit_log_updates`).

## User story

> As a security-conscious maintainer, **I want** tests that prove our
> RLS policies block the operations they're supposed to block,
> **so that** a future schema change can't silently widen the surface
> without a red CI signal.

## Acceptance criteria

- **AC-1**: New Vitest config `vitest.integration.config.ts` runs the
  integration spec against a local Supabase at `http://127.0.0.1:54321`.
- **AC-2**: New script `npm run test:integration` invokes that config.
- **AC-3**: Fixture `tests/integration/security/setup-supabase.ts` mints
  four JWTs (anon / userA / userB / admin) via the local service-role
  key (gitignored `.env.test.local`).
- **AC-4**: Spec `tests/integration/security/rls-enforcement.test.ts`
  has at least one `describe` block per table below, with `it()` cases
  for every contracted permission:
  - `attempts` — anon INSERT ok; UPDATE allowed only on demographics
    columns; UPDATE on `score`/`correct_count` blocked by trigger
    `forbid_attempt_score_changes`; DELETE allowed when
    `share_id IS NOT NULL`.
  - `audit_log` — anon SELECT blocked; UPDATE blocked; INSERT only via
    `log_audit_event` SECDEF function.
  - `user_roles` — anon cannot read; non-admin cannot self-grant a
    role; `has_role()` SECDEF honours its pinned `search_path`.
  - `respondent_session_tokens` — anon cannot read/write; SECDEF RPCs
    are the only ingress.
  - `dsr_requests` — user can INSERT their own; user cannot read
    others' rows; admin can read all.
  - `profiles` — userA cannot UPDATE userB's row; demographics-only
    update path (the single permitted UPDATE path per CLAUDE.md).
- **AC-5**: Session-token grace-window test (per migration
  `20260520800000_session_token_dod.sql`): after the 7-day cutoff,
  RPCs reject calls lacking `p_session_token`.
- **AC-6**: GitHub Actions job `rls-tests` boots local Supabase and
  runs `npm run test:integration`. `continue-on-error: true` on PRs
  until the suite is stable; flip to required after a week of green.

## Risks

| Risk | Mitigation |
|---|---|
| Local Supabase boot is slow → CI minutes burn | Suite runs only on PRs touching `supabase/**`, `tests/integration/**`, or `src/integrations/supabase/**` via `paths` filter. |
| Service-role key in `.env.test.local` accidentally committed | Add to `.gitignore` and add a CI grep gate that fails the build if the file is ever committed. |
| Fixture seed drift over time | Seed is deterministic and lives in the fixture file; any migration that breaks it triggers an obvious test failure. |
