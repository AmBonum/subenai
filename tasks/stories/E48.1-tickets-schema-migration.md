# E48.1 — Support tickets schema + RLS + RPCs + audit triggers

**Epic:** E48 — Support contact form + admin ticketing system
**Effort:** `M` (~2 days; +0.5 day after Phase-A pre-implementation review absorbed C-S1/C-S2/C-DB1/C-DB2 + 6 HIGH findings)
**Priority:** `P0`
**Status:** 🟡 Ready — Phase-A review integrated 2026-05-21
**Branch:** `feature/E48-support-ticketing`
**Commit prefix:** `feat(db):`
**Dependencies:** none (this is the first story in the epic)

## Context

E48 ships an end-to-end support ticketing surface. Everything downstream
(file uploads, admin UI, notifications) reads or writes through the tables
introduced here. Schema must be locked down before any UI work begins,
because every later story depends on the RLS contract.

The migration introduces four tables (`support_tickets`,
`support_ticket_messages`, `support_ticket_attachments`,
`admin_notification_preferences`), four RPCs, three enums, audit triggers,
a server-side notification-fanout trigger, and the standard
`ENABLE ROW LEVEL SECURITY` lockdown. It also slots a mirror block into
`DEPLOY_SETUP.sql` so a from-scratch bootstrap stays working.

**Architectural decision absorbed from Phase-A security review (C-S1, C-S2):**
the `anon` role has **NO direct INSERT privilege** on `support_tickets`,
`support_ticket_messages`, or `support_ticket_attachments`. Anonymous
submissions go through `submit_support_ticket()` SECURITY DEFINER RPC,
called by the CF function `/functions/api/support-ticket-create.ts`
using the service-role key. The CF function is where Turnstile +
honeypot + rate-limit live; the RPC owns server-side `view_token`
generation. This removes the entire "anon forges view_token" attack
class because anon cannot reach the table at all.

See PLAN §"Data model", §"RLS policies", §"RPCs" for the precise shape.

## Acceptance criteria

### Schema

- **AC-1 (tables):** Migration file `supabase/migrations/<timestamp>_e48_1_support_tickets_schema.sql` creates the four tables with constraints. Notable column rules absorbed from review:
  - `support_tickets.subject` — `text CHECK (char_length(subject) BETWEEN 1 AND 200)`, immutable after insert (enforced by RLS UPDATE policy that excludes this column from the allowed set)
  - `support_tickets.body` — `text CHECK (char_length(body) BETWEEN 1 AND 5000)`, immutable after insert (same mechanism)
  - `support_tickets.submitter_email` — `text NOT NULL CHECK (char_length(submitter_email) BETWEEN 5 AND 254 AND submitter_email ~ '^[^@]+@[^@]+\.[^@]+$')` (M-S2 length cap)
  - `support_tickets.source` — `support_ticket_source NOT NULL DEFAULT 'public_form'` (H-DB1: was free text)
  - `support_tickets.assigned_to` — `uuid REFERENCES auth.users(id) ON DELETE SET NULL` (C-DB2: was unspecified)
  - `support_tickets.view_token_hash` — `text NOT NULL CHECK (view_token_hash ~ '^[0-9a-f]{64}$')` (L-DB2: column-level defence-in-depth)
  - `support_tickets.view_token_expires_at` — `timestamptz NOT NULL`
  - `support_tickets.view_token_invalidated_at` — `timestamptz` (H-S3: revocation path)
  - `support_ticket_attachments.size_bytes` — `integer NOT NULL CHECK (size_bytes > 0 AND size_bytes <= 5242880)`
  - `support_ticket_attachments.storage_path` — `text NOT NULL`; path derived **server-side only** as `<ticket_id>/<crypto.randomUUID()>.<ext>` where `<ext>` comes from a hardcoded `{image/png: 'png', image/jpeg: 'jpg', application/pdf: 'pdf'}` map (M-S1)
  - `admin_notification_preferences.channels` — `jsonb NOT NULL DEFAULT '{"email": true, "in_app": true}' CHECK (channels ? 'email' AND channels ? 'in_app')` (M-DB3)
  - `admin_notification_preferences.per_category` — `jsonb NOT NULL CHECK (per_category ?& ARRAY['bug','question','feature_request','abuse_report','billing','gdpr','other'])` (M-DB3)
  - Migration header comment notes the deliberate trade-off of using Postgres `ENUM` for status/category/source vs CHECK-constrained text (M-DB2)

- **AC-2 (enums):** Three new enums:
  - `support_ticket_status`: `new`, `in_progress`, `waiting_user`, `resolved`, `reopened`, `archived` (M-DB1: added `reopened`)
  - `support_ticket_category`: `bug`, `question`, `feature_request`, `abuse_report`, `billing`, `gdpr`, `other`
  - `support_ticket_source`: `public_form`, `app_form` (H-DB1)
  - `support_attachment_scan_status`: **`clean`, `error`** only (C-DB1: collapsed from 4 values)
  - `scan_provider` column **dropped** entirely (C-DB1); `scan_result` jsonb column **dropped** (L-S2, L-DB1) — re-add both in the follow-up VirusTotal epic if it ships.

- **AC-3 (RLS — anon path is closed at the role layer):**
  - `support_tickets`: NO `anon` INSERT policy. `authenticated` user: SELECT/INSERT own (`submitter_user_id = auth.uid()`). `admin`: ALL (gated by `public.has_role(auth.uid(), 'admin')`). UPDATE policy explicitly forbids changing `subject`, `body`, `submitter_email`, `submitter_name`, `view_token_hash`, `view_token_expires_at`, `created_at` after insert (H-DB4 — body/subject immutability).
  - `support_ticket_messages`: SELECT/INSERT via ticket-FK lookup; admins ALL; no anon access. The view-thread anonymous read path goes through a SECURITY DEFINER RPC `get_ticket_thread_for_view_token(p_ticket_id, p_view_token)` that validates the token, NOT through table-level RLS.
  - `support_ticket_attachments`: same pattern as messages.
  - `admin_notification_preferences`: owner-only SELECT/INSERT/UPDATE; no admin-of-admin override.
  - `storage.objects` for the `support-attachments` bucket: anon = no access; authenticated = no access; admins SELECT only; INSERT via service-role only (enforced at bucket policy level in E48.2).
  - `ALTER TABLE … ENABLE ROW LEVEL SECURITY` on every new table.

- **AC-4 (RPCs — four total):**
  - `submit_support_ticket(p_payload jsonb) RETURNS jsonb` — SECURITY DEFINER. Accepts subject/body/category/email/name/user_id/source/user_agent/ip_country. **Generates** view_token + view_token_hash internally via `gen_random_bytes(32)` + `encode(digest(..., 'sha256'), 'hex')`; returns `{ticket_id, view_token}` (plain token, one-time response). NO RLS-policy reliance for anon — the function does its own role-based branching: when called by `service_role` it accepts an anonymous insert (no auth.uid()); when called by `authenticated`, it requires `p_payload->>'user_id' = auth.uid()::text`. **`GRANT EXECUTE TO service_role, authenticated`** — `anon` is NOT granted (C-S2 closure).
  - `request_attachment_signed_url(p_attachment_id uuid) RETURNS text` — SECURITY DEFINER. Validates `public.has_role(auth.uid(), 'admin')` AND `auth.jwt() ->> 'aal' = 'aal2'` AND `scan_status='clean'`; writes `audit_log` row `action='support_attachment_download_url_issued'`; returns a 15-min signed URL with `Content-Disposition: attachment; filename=<sanitised>` (L-S1). **`GRANT EXECUTE TO authenticated`** only.
  - `transition_ticket_status(p_ticket_id uuid, p_new_status support_ticket_status, p_note text) RETURNS jsonb` — SECURITY DEFINER. Admin + AAL2 gate. Validates the state-machine transition (legal moves: `new → in_progress`, `in_progress → waiting_user|resolved`, `waiting_user → in_progress|resolved`, `resolved → reopened|archived`, `reopened → in_progress`, any → soft-delete via `deleted_at`). Writes `audit_log`. **`GRANT EXECUTE TO authenticated`** only.
  - `get_ticket_thread_for_view_token(p_ticket_id uuid, p_view_token text) RETURNS jsonb` — SECURITY DEFINER. Computes `digest(p_view_token, 'sha256')` and compares to `view_token_hash`; checks `view_token_expires_at > now() AND view_token_invalidated_at IS NULL`; writes `audit_log` row `action='support_ticket_view_token_used'` with `ip_country` from CF header (M-S4); returns the thread (subject, status, messages, attachments — but attachment download URLs NOT issued; see PLAN open question). **`GRANT EXECUTE TO anon, authenticated`** (token IS the auth).

### Indexes

- **AC-5 (indexes):**
  - `CREATE INDEX support_tickets_admin_working_set_idx ON support_tickets (status, created_at DESC) WHERE deleted_at IS NULL AND archived_at IS NULL` (H-DB3 — partial index)
  - `CREATE INDEX support_tickets_submitter_email_lower_idx ON support_tickets (lower(submitter_email))` (H-DB2 — GDPR lookup path)
  - `CREATE INDEX support_tickets_assigned_to_idx ON support_tickets (assigned_to) WHERE assigned_to IS NOT NULL`
  - `CREATE INDEX support_tickets_category_status_idx ON support_tickets (category, status) WHERE deleted_at IS NULL`
  - `CREATE INDEX support_tickets_fts_idx ON support_tickets USING GIN (to_tsvector('simple', subject || ' ' || body)) WHERE deleted_at IS NULL`
  - `CREATE INDEX support_ticket_messages_ticket_id_created_at_idx ON support_ticket_messages (ticket_id, created_at)`
  - `CREATE INDEX support_ticket_attachments_ticket_id_idx ON support_ticket_attachments (ticket_id)`

### Audit + notifications

- **AC-6 (audit triggers):**
  - `support_tickets`: trigger on `UPDATE` of `status`, `assigned_to`, `deleted_at`, `archived_at`, `view_token_invalidated_at` writes `audit_log` via `public.log_audit_event(...)`. `body`/`subject`/`submitter_email` are enforced immutable by the UPDATE RLS policy (H-DB4), but the trigger additionally raises if any of these columns is in `NEW.* IS DISTINCT FROM OLD.*` — defence in depth against a future SECURITY DEFINER RPC that might bypass RLS.
  - `support_ticket_attachments`: trigger on `INSERT` writes `audit_log` `action='support_attachment_inserted'`.
  - `support_ticket_messages`: trigger on `INSERT` writes `audit_log` `action='support_message_inserted'` (the existing E40/E46 pattern).

- **AC-7 (server-side notification fan-out — H-S4 fix):**
  Trigger `AFTER INSERT ON support_tickets` calls a SECURITY DEFINER function `enqueue_admin_notifications_for_ticket(p_ticket_id)` that:
  1. Queries every admin's `admin_notification_preferences`.
  2. For each admin with `enabled=true AND per_category->>(NEW.category) = 'true'`: writes an entry into `notifications` (existing table) with `event_type='support_ticket_new'`, `user_id=admin_id`. This guarantees notification rows exist whether or not any admin browser is open at the moment of insertion. Browser handlers only render/increment-badge from existing rows.
  3. Fires `pg_notify('support_tickets_admin', payload)` so an active admin browser updates in real-time.
  Same pattern for `AFTER INSERT ON support_ticket_messages` where `author_kind='user'`.

### Mirror + types + tests

- **AC-8 (`DEPLOY_SETUP.sql`):** Mirror block added at end of file (after E46.6 section), following existing pattern: header comment with epic ID + slug, table DDL, indexes, RLS, RPCs, triggers.
- **AC-9 (`types.ts`):** Hand-extended with four table shapes + four RPC signatures. Per CLAUDE.md the types file is kept in sync manually.
- **AC-10 (Vitest contract test — `tests/db/support-tickets-schema.test.ts`):** Greps the migration file and asserts:
  - all four tables exist
  - RLS is enabled on each
  - the named policies exist (the count is checked, not free-form)
  - every `CREATE TABLE` is followed by `ENABLE ROW LEVEL SECURITY`
  - the four RPCs declare `SECURITY DEFINER`
  - `anon` is granted EXECUTE only on `get_ticket_thread_for_view_token` (C-S2 anti-regression)
  - `scan_status` enum has exactly two values
  - `scan_provider`, `scan_result` columns are NOT in the migration text
  - `assigned_to` line contains `ON DELETE SET NULL`
- **AC-11 (Vitest lockdown test — `tests/db/support-tickets-rls-lockdown.test.ts`):**
  - anon: cannot INSERT into `support_tickets` directly → 403/permission-denied
  - anon: cannot SELECT from `support_tickets` directly → 0 rows or 403
  - anon: CAN call `get_ticket_thread_for_view_token` with a valid (ticket_id, token) pair (positive test)
  - anon: with wrong token → 0 rows / null return
  - anon: with right token but expired → null
  - anon: with right token but invalidated → null
  - authenticated user (audit-bot): can INSERT own ticket via RPC; CANNOT INSERT with someone else's `submitter_user_id`
  - authenticated user: can SELECT own tickets; cannot SELECT someone else's
  - **IDOR coverage (C-S3):** authenticated non-admin user passes a real other-user attachment UUID to `request_attachment_signed_url` → permission-denied / null (not a leak)
  - admin without AAL2 → permission-denied on the signed-URL and transition RPCs
  - admin with AAL2: full read + write paths work

## Open questions

- **Should `ip_country` be backfilled from CF-IPCountry on every submission or made nullable for now?** *Lean: nullable, populated when present.* CF header is the source; only available behind CF Pages, not in local dev.
- **Should `get_ticket_thread_for_view_token` also issue attachment download URLs to anonymous users?** *Lean: no.* The view-thread page shows filenames + sizes + a "súbor je k dispozícii len pre administrátora" note. Reduces signed-URL surface area and avoids issuing 15-min-TTL URLs to fresh-anonymous sessions.
- **Enum vs CHECK-constrained text for status/category/source?** Documented as deliberate trade-off in the migration header per M-DB2 — enums chosen for type safety; ADD VALUE is the only forward path.
