# E35.3 — Input / XSS / prompt-injection boundary fuzz suite

**Epic:** [E35 — Security & GDPR compliance audit + test coverage expansion](../PLAN-2026-05-20-E35-security-compliance-audit.md)
**Effort:** `M` (≤ 2 days)
**Priority:** `P1` (must)
**Status:** 🟡 Ready

## Context

The XSS surface is small but real: `src/routes/changelog.tsx` calls
`renderInline()` which feeds escaped-then-rewritten HTML into
`dangerouslySetInnerHTML`; blog posts render user-controlled-from-DB
Markdown via `react-markdown`; share_id URL params are reflected into
the DOM through router state. The recon also flagged two client surfaces
that pass user-controlled dicts to Supabase RPCs without zod validation:
`startRespondentSession` (intake dict) and most admin CRUD wrappers in
`src/lib/admin/queries.ts`.

The `VITE_AI_GENERATOR_ENABLED` backend (AH-11) is not yet wired, but
the prompt-injection harness lands now so the moment it ships the
hostile-payload coverage is one assertion-flip away.

## User story

> As a security-conscious maintainer, **I want** every place that
> ingests user input to be hammered with hostile payloads in tests,
> **so that** an XSS or prompt-injection regression cannot land
> silently.

## Acceptance criteria

- **AC-1**: New `tests/security/xss-payloads.ts` exports a curated
  payload list (~25 entries from the OWASP XSS Filter Evasion cheat
  sheet — no third-party dependency).
- **AC-2**: New `tests/security/changelog-sanitisation.test.ts` renders
  `renderInline()` with each payload and asserts the rendered HTML
  contains no unescaped `<script`, `<img onerror`, `<iframe`,
  `javascript:`, or `on*` event handler.
- **AC-3**: New `tests/security/blog-markdown.test.ts` renders the
  blog post body component with hostile Markdown (including
  `[link](javascript:alert(1))`, raw `<script>`, IMG with onerror) and
  asserts none of the listed dangerous patterns reach the DOM.
- **AC-4**: New `tests/security/share-id-param.test.ts` mounts
  `/r/$shareId` and `/t/$shareId` routes with malicious shareId values
  and asserts no reflected XSS occurs. (Today's regex `^[a-zA-Z0-9]{6,12}$`
  constraint means most payloads never reach the DB — the test
  documents that and locks the regex.)
- **AC-5**: New `tests/security/rpc-input-contract.test.ts` calls the
  client wrappers (`startRespondentSession`,
  `updateQuestion`/`updateTest`/`updateCategory` in `src/lib/admin/queries.ts`)
  with malformed payloads (oversized strings, control characters,
  prototype pollution attempts, mismatched types) and asserts the
  server-side response. Expected-red allowed where the contract is
  documented as "no client validation yet, server constraint catches" —
  these reds map to E39 follow-up.
- **AC-6**: New `tests/security/prompt-injection-payloads.ts` exports
  a payload list (jailbreak attempts, prompt-escape patterns, control
  characters, oversized inputs).
- **AC-7**: New `tests/security/prompt-injection-harness.test.ts`
  imports the payloads, asserts the `/api/admin/ai-generate` endpoint
  currently returns `disabled` (because AH-11 backend not wired), and
  exports the harness for re-use when AH-11 lands. Includes a `it.todo`
  per payload so the future engineer can flip them to `it()` without
  rewriting the structure.

## Risks

| Risk | Mitigation |
|---|---|
| OWASP cheat sheet payloads contain trivially escaped characters → tests pass trivially | At least 5 payloads must include known bypass patterns (e.g. `<svg/onload>`, `<math href=javascript:>`, polyglot). |
| Reviewer cannot verify payloads from screenshots | Tests run headless and assert against the actual rendered HTML string, not visual screenshots. |
