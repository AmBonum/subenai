**Epic:** [E35 — Security & GDPR compliance audit + test coverage expansion](../PLAN-2026-05-20-E35-security-compliance-audit.md)

**Priority:** `P2` (should)
**Status:** 🟡 Files ready, awaiting `.github/**` approval

## Context

The existing test coverage (Vitest unit + Playwright e2e) is **white-box**
— it reaches into the codebase and asserts contracts on the source. A
black-box scanner sees what an attacker sees: the served HTTP response,
the cookies set, the headers missing, the form fields exposed.

OWASP ZAP is the industry-standard free DAST scanner. The official
GitHub Actions (`zaproxy/action-baseline`, `zaproxy/action-full-scan`)
are free for public repos and free-tier private repos. No paid SaaS.

This story wires:
1. **`zap-baseline.yml`** — passive scan, weekly + on-demand. ~3-5 min
   runtime. Targets production by default; preview deploys on-demand.
2. **`zap-full-scan.yml`** — active scan, on-demand only. ~30-60 min.
   Includes a hard guard against accidentally pointing at production.
3. **`.zap/rules.tsv`** — per-rule severity overrides with documented
   IGNORE reasons. Starts permissive (`fail_action: false`) so the
   first runs don't block work; ratchets up after triage.

## User story

> As the operator, **I want** OWASP ZAP scanning the live site
> weekly + on-demand, **so that** misconfigured headers, leaked
> cookies, or new info-disclosure findings are caught by an external
> tool that doesn't share the same blind spots as our internal tests.

## Operational notes

### When to flip from WARN to FAIL

A rule is ready to FAIL when:
1. Two consecutive baseline runs report zero findings for it.
2. The rule has been manually reviewed and we're confident a future
   finding would represent a real regression, not a noise change.

### How to add a new IGNORE

1. Add a `# comment` block above the rule line in `.zap/rules.tsv`
   explaining the documented accepted risk.
2. If the risk needs follow-up (e.g. "remove this when E40 ships"),
   link the follow-up epic in the comment.

### Cost

- ZAP itself: Apache 2.0, free.
- `zaproxy/action-baseline`: free for public repos; included in
  GitHub Free for private repos within the standard Actions minutes
  quota.
- `zaproxy/action-full-scan`: same.
- No SaaS, no API key, no rate-limit account.

### Threat coverage

Baseline (passive) covers:
- HTTP security headers (CSP, HSTS, X-Frame-Options, etc.) — overlap
  with `tests/security/headers-contract.test.ts` but from outside.
- Cookies (HttpOnly, Secure, SameSite) — finds gaps the unit tests
  can't see because they don't observe the live Set-Cookie response.
- Info disclosure (server versions, source maps, comments).
- Open redirects, missing CSRF tokens (heuristic).

Full scan (active) adds:
- SQL injection, XSS, path traversal payloads.
- Authentication bypass attempts on `/login`, `/auth/*`.
- Brute-force on forms (rate-limited by Turnstile + our own caps).

## Risks

| Risk | Mitigation |
|---|---|
| First baseline run reports many findings → workflow looks broken | `fail_action: false` ensures the run is observational, not blocking. |
| Full scan accidentally hits production | Bash guard in `zap-full-scan.yml`. Reviewer confirms in CR. |
| ZAP false positives waste triage time | `.zap/rules.tsv` with documented IGNOREs; ratchet to FAIL only after green baseline. |
| Action gets a major version bump that breaks the integration | Pin to `@v0.13.0` / `@v0.10.0`. Dependabot (E35.7) will surface updates as PRs we review individually. |
